The GEM handles we saw in Part 4 are only valid within a drm_file. For a display server (compositor) to receive a buffer rendered by an application, or for a camera or video decoder to read a buffer created by a GPU, a sharing mechanism passable via an fd is required. This article walks through that mechanism, dma-buf, and PRIME, the DRM feature that bridges GEM and dma-buf.

PRIME: Sharing Buffers Between Processes and Devices

GEM handles are meaningful only within a drm_file and cannot be passed directly to other processes. For a display server (compositor) to receive buffers drawn by applications, or for a camera/video decoder to read buffers produced by the GPU, a sharing mechanism that can be passed as an fd is necessary. Linux's answer to this is dma-buf, and the DRM feature bridging GEM and dma-buf is called PRIME.

  • The exporter wraps its buffer into a struct dma_buf and exposes it as an fd.
  • The importer calls dma_buf_attach() with that fd, then dma_buf_map_attachment() to obtain an sg_table (list of physical pages) and creates its own buffer object.
  • Data is not copied. Both sides view the same physical pages.

It reserves an fd, acquires the dma-buf, and associates it with that fd using fd_install(). The key function responsible for acquiring the dma-buf is drm_gem_prime_handle_to_dmabuf().
drivers/gpu/drm/drm_prime.c - drm_gem_prime_handle_to_dmabuf() (L431-494)
c
Source drivers/gpu/drm/drm_prime.c L431-L494 (Linux v6.19)
The branching logic inside this function forms the core of this section:
  1. drm_gem_object_lookup(): Looks up the object by handle.
  2. If already exported in this file (drm_prime_lookup_buf_by_handle), it returns that dma-buf as-is.
  3. If it is an imported object, it returns the original dma-buf (obj->import_attach->dmabuf).
  4. If obj->dma_buf already exists, it is reused.
  5. A new one is created only when none of the above exist (export_and_register_object).
Thus, exporting the same handle multiple times still yields the exact same dma-buf. This explains why export #1 and export #2 point to the identical inode in the example below.

import: dma-buf fd → handle

The receiving end calls DRM_IOCTL_PRIME_FD_TO_HANDLE.
drivers/gpu/drm/drm_prime.c - drm_gem_prime_fd_to_handle() (L292-359)
c
Source drivers/gpu/drm/drm_prime.c L292-L359 (Linux v6.19)
It acquires the dma-buf from the fd via dma_buf_get(fd). If it is an already-known dma-buf, the existing handle is returned. If it is encountered for the first time, a GEM object is created via drm_gem_prime_import(), and it is registered into this file's handle table with drm_gem_handle_create_tail(). During object creation, two distinct cases exist:
drivers/gpu/drm/drm_prime.c - drm_gem_prime_import_dev() (L968-1020)
c
Source drivers/gpu/drm/drm_prime.c L968-L1020 (Linux v6.19)
  • If the dma-buf was exported by the same DRM device (drm_gem_is_prime_exported_dma_buf), no new object is created; it simply increments the reference count on the original object (dma_buf->priv). Sharing within the same device incurs virtually zero overhead.
  • If it was exported by a different device, an sg_table is obtained via dma_buf_attach() → dma_buf_map_attachment_unlocked(), and the driver callback gem_prime_import_sg_table() instantiates its own GEM object backed by those pages. Because obj->import_attach is populated, the object is subsequently treated as an "imported object" (e.g., drm_gem_dumb_map_offset() shown earlier returns -EINVAL for imported objects).

Summary

Key takeaways from this post:
  • dma-buf = a pseudo file backed by an anonymous inode + operation table + private data. Being an fd, it can be passed to other processes via SCM_RIGHTS.
  • export (drm_gem_prime_handle_to_dmabuf) searches cache first, creating a new instance only when none exists. Exporting the same handle multiple times yields the exact same dma-buf.
  • import (drm_gem_prime_import_dev) reuses the original object directly if exported by the same device; if from a different device, it invokes attach → map_attachment to obtain an sg_table and creates an object via the driver callback. Data is never copied.
