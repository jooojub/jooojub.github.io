Why Is Memory Management DRM's Job

Because the GPU is a separate processor from the CPU, rendering graphics requires both the CPU and GPU to manage the same memory together. Textures, framebuffers, and command buffers all fall into this category. This presents challenges that cannot be solved with standard malloc.
  • To allow GPU access, memory must be pinned to physical pages and mapped into a GPU-accessible address space (via an IOMMU or the GPU's own page table).
  • When a process terminates, the GPU memory it occupied must be automatically reclaimed.
  • Different processes must view the same buffer, such as a display server and a client application.
  • Synchronization is required so that the CPU does not modify a buffer while the GPU is actively accessing it.
DRM solves this problem through an interface called GEM (Graphics Execution Manager). It represents every GPU buffer as a single struct drm_gem_object, while a backend (helper) determines where the actual memory is sourced. Representative examples include drm_gem_shmem_helper.c, which uses main memory shmem; drm_gem_dma_helper.c, which uses contiguous memory; and TTM-based drm_gem_ttm_helper.c, which manages dedicated GPU memory (VRAM) as well. The code in this post follows the simplest shmem backend (used by drivers like vkms).

The Name Tag: Handles Are per fd

Userspace cannot directly know the object's kernel pointer. Instead, it receives an integer handle. This handle is an index into drm_file.object_idr introduced in Part 1. In other words, handles reside in an independent namespace for each open()ed file descriptor (fd); even for the exact same object, different processes can have different handles.

Code Flow 1: Creating a Dumb Buffer

Let us trace GEM through the simplest buffer creation path: the dumb buffer. This is the most basic buffer used for software rendering on screen; it lacks GPU acceleration features and is essentially "flat memory that the CPU can paint into." Userspace creates one using a single ioctl: DRM_IOCTL_MODE_CREATE_DUMB.

The operational sequence unfolds as follows:
  1. drm_gem_shmem_create() creates the object with an initial reference count of 1.
  2. drm_gem_handle_create() creates the handle. Internally, drm_gem_object_handle_get() increments handle_count, taking an additional object reference only when it is the first handle (if (obj->handle_count++ == 0) drm_gem_object_get(obj)). Subsequent handles simply increment the counter.
  3. Finally, drm_gem_object_put() drops the initial reference (source comment: "handle holds it now"). The object's lifecycle is now tied to the handle. When userspace closes the handle, or when the file is closed, drm_gem_release() releases all remaining handles in that file's object_idr, freeing the object.

Code Flow 2: Painting from the CPU with mmap

Although the buffer has been created, the CPU cannot access it yet. Because multiple buffers reside behind the single /dev/dri/card0 file descriptor, calling mmap(fd, ...) alone does not identify which buffer to map. DRM solves this using a fake offset, repurposing the file offset (the final argument to mmap) as an object identifier.

When userspace first reads or writes to the mapped address, a page fault occurs, and the object's fault handler maps the backing pages into the page table entries one by one.

Through this mechanism, a single user line such as *(uint32_t *)(px + ...) = color writes directly into the shmem pages backing the GEM object.

Summary

In this post, we have explored the following:
  • GPU buffers are represented by a single GEM object, which userspace references via an independent handle per fd (drm_file). The handle's lifetime governs the object's lifetime.
  • Dumb buffers are implemented through a shmem file + mmap fake offset, with physical pages allocated on demand when first needed.
  • mmap resolves the object via the fake offset and maps backing pages one by one upon a page fault. drm_vma_node_is_allowed() prevents unauthorized processes from mapping arbitrary buffers by simply knowing their offset.
Handles are meaningful only within their originating drm_file. Next, we will explore how to share these buffers with other processes or hardware devices using PRIME and dma-buf.
