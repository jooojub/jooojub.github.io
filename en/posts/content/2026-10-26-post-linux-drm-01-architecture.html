Introduction

Drawing anything on the screen in Linux goes through a kernel subsystem called DRM (Direct Rendering Manager). Desktop Wayland or Xorg, Android's SurfaceFlinger, and even the Raspberry Pi console display all operate on top of the same DRM.
This has nothing to do with Digital Rights Management (copyright protection), which shares a similar name; this article deals exclusively with the Linux kernel's graphics subsystem.
In this post, we explore what DRM is and how it connects to the kernel. We will delve deeply into the actual code starting in the next post.

Why DRM Was Needed

Before DRM existed, there were two primary approaches:
  • fbdev (/dev/fb0): A straightforward method that mmaps a single chunk of display memory to directly write pixels. It lacks features such as 3D acceleration, multi-monitor support, and resolution changes.
  • Direct hardware control by the X server: The X server ran with root privileges to directly access graphics card registers, configuring resolutions (modes) and sending 3D commands.
The second approach had several critical problems:
  • For 3D applications to use the GPU directly, the kernel needed to arbitrate GPU access, but no such mechanism existed (concurrent GPU access by multiple processes caused mutual corruption).
  • Because resolution configuration (mode setting) lived in user space, switching between console and X caused screen flickering, and controlling early boot splash screens was impossible.
  • The requirement for the X server to run as root posed severe security vulnerabilities.
DRM solved these issues by establishing a model where "the kernel manages the GPU and display, while user space accesses them strictly through safe interfaces." The major milestones were roughly as follows:
FeatureRoleApproximate Era
DRI / DRMApplications send commands directly to the GPU under kernel mediationLate 1990s ~ around 2000
GEMKernel manages GPU buffers (memory)Around Linux 2.6.28
KMSResolution/display configuration moved into kernelAround Linux 2.6.29
dma-buf (PRIME)Shares buffers across processes and devicesAround Linux 3.3
render nodeDedicated nodes for GPU compute without display controlAround Linux 3.12
atomic modesetAtomically verifies and applies display configuration changesLinux 3.19 (Kernel doc Documentation/gpu/todo.rst)
The structures covered in this article are the results of this history. Keep in mind that a single subsystem handles both rendering (drawing with GPU) and display (outputting to screen).

  • Applications draw using OpenGL/Vulkan. Mesa, which implements these APIs, generates GPU-specific commands (shaders, state setup). This part is called the user-mode driver (UMD).
  • libdrm is a thin C library wrapping ioctl(). In other words, user space communicates with DRM solely by opening /dev/dri/* files and issuing ioctl, mmap, and read.
  • The kernel side is divided into the common DRM core, helpers shared across various drivers, and hardware-specific drivers.
Two pathways are visible in the diagram. 3D applications use the render node solely for GPU compute, while display configuration is handled by the display server (compositor) through the primary node (card0). This separation is at the heart of DRM's design.

How card0 Differs from renderD128

The primary node (card0) has access to all capabilities (including KMS) and can hold DRM master, the privilege required for display control. The render node (renderD128), while unable to configure displays, is free from permission constraints. Anyone with file access permissions can open it to run GPU computations.
This distinction is baked into each ioctl via flags and enforced by drm_ioctl_permit().
include/drm/drm_ioctl.h - enum drm_ioctl_flags (L80-122)
c
Source include/drm/drm_ioctl.h L80-L122 (Linux v6.19)
drivers/gpu/drm/drm_ioctl.c - drm_ioctl_permit() (L599-621)
c
Source drivers/gpu/drm/drm_ioctl.c L599-L621 (Linux v6.19)
Reading through the code makes the rules clear:
  • An ioctl flagged with DRM_MASTER can only be invoked by the current master. A prime example is DRM_IOCTL_MODE_ATOMIC.
  • Render nodes (drm_is_render_client) can only execute ioctls where DRM_RENDER_ALLOW is explicitly designated. Hence, while DRM_IOCTL_VERSION and DRM_IOCTL_PRIME_HANDLE_TO_FD work on render nodes, DRM_IOCTL_MODE_CREATE_DUMB has flags set to 0 and is rejected on render nodes.
Then who becomes the master? The first client to open the primary file automatically acquires master status.
drivers/gpu/drm/drm_auth.c - drm_master_open() (L317-335)
c
Source drivers/gpu/drm/drm_auth.c L317-L335 (Linux v6.19)
Therefore, if the desktop environment has already opened card0 and holds master privileges, any other application attempting display configuration (atomic commit) on that same card0 will receive -EACCES.

drm_driver: The Template Drivers Fill In

A driver defines a single struct drm_driver as const. Inside are feature flags, file operations, a driver-specific ioctl table, and several callbacks.
include/drm/drm_drv.h - struct drm_driver (L181-434)
c
Source include/drm/drm_drv.h L181-L434 (Linux v6.19)
  • driver_features: Bit flags such as DRIVER_GEM, DRIVER_MODESET, DRIVER_RENDER, and DRIVER_ATOMIC. The DRM core inspects this value to decide which features to activate (for instance, DRIVER_RENDER must be present to instantiate a render node).
  • fops: The file_operations for /dev/dri/cardN. Most drivers use a standard macro for this (seen below).
  • ioctls, num_ioctls: Driver-specific ioctl table. The number range is 0x40 through 0xA0 (DRM_COMMAND_BASE to DRM_COMMAND_END).
  • dumb_create, gem_prime_import_sg_table, etc.: Driver callbacks invoked by the core. The core handles common tasks and delegates hardware-dependent behavior to these callbacks. This pattern permeates all of DRM.
include/drm/drm_drv.h - enum drm_driver_feature (L57-170)
c
Source include/drm/drm_drv.h L57-L170 (Linux v6.19)

drm_file: One per open()

Each open() of /dev/dri/card0 spawns a struct drm_file. All per-process (or per-fd) states reside here.
include/drm/drm_file.h - struct drm_file (L164-420)
c
Source include/drm/drm_file.h L164-L420 (Linux v6.19)
  • object_idr: A table mapping user-visible GEM handles to kernel objects. This implies handles are isolated per fd (drm_file).
  • event_list, pending_event_list: Queues buffering events such as page flip completion. User space retrieves them by calling read() on this fd.
  • atomic, universal_planes: Client capabilities enabled via drmSetClientCap(). Atomic ioctls require these to be turned on.
  • master, is_master: Indicate whether this file holds display control authority.

Summary

Here is what we covered in this post:
  • DRM is a subsystem through which the kernel arbitrates rendering (GPU) and display (KMS); user space interfaces with it solely via ioctl, mmap, and read on /dev/dri/*.
  • Device nodes use major number 226 and include primary (card) and render (renderD) nodes, with permission distinctions enforced through ioctl flags (DRM_MASTER, DRM_RENDER_ALLOW).
  • The hierarchy is structured as drm_driver (template) → drm_device (device) → drm_minor (node) → drm_file (open), with the core handling common tasks and delegating hardware-specific routines to driver callbacks.
In the next post, we will walk through the code of the vkms driver to trace the process by which this architecture is materialized: core initialization (registering 226) and driver registration (drm_dev_register).
