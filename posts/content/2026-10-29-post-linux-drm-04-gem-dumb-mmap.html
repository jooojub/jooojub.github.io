Why Is Memory Management DRM's Job

GPU는 CPU와 별개의 프로세서라서, 그림을 그리려면 CPU와 GPU가 같은 메모리를 함께 다뤄야 합니다. 텍스처, 프레임 버퍼, 명령 버퍼가 모두 그런 메모리입니다. 여기에는 일반 malloc으로 풀 수 없는 문제가 있습니다.
  • GPU가 접근하려면 메모리가 물리 페이지로 고정(pin)되어 있어야 하고, GPU용 주소(IOMMU나 GPU 자체 페이지 테이블)로 매핑되어야 합니다.
  • 프로세스가 죽으면 그 프로세스가 쓰던 GPU 메모리는 자동으로 회수되어야 합니다.
  • 화면 서버와 앱처럼 다른 프로세스가 같은 버퍼를 봐야 합니다.
  • GPU가 쓰는 중에 CPU가 건드리지 않도록 동기화가 필요합니다.
DRM은 이 문제를 GEM(Graphics Execution Manager)이라는 인터페이스로 풉니다. 모든 GPU 버퍼를 struct drm_gem_object 하나로 표현하고, 실제 메모리를 어디서 가져올지는 백엔드(helper)가 정합니다. 메인 메모리의 shmem을 쓰는 drm_gem_shmem_helper.c, 연속 메모리를 쓰는 drm_gem_dma_helper.c, GPU 전용 메모리(VRAM)까지 관리하는 TTM 기반 drm_gem_ttm_helper.c가 대표적입니다. 이 글의 코드는 가장 단순한 shmem 백엔드(vkms 등이 사용)로 따라가겠습니다.

The Name Tag: Handles Are per fd

유저는 객체의 포인터를 알 수 없습니다. 대신 정수 handle을 받습니다. 이 handle은 1편에서 본 drm_file.object_idr의 인덱스입니다. 즉 handle은 open()한 파일(fd)마다 독립적인 번호 공간이고, 같은 객체여도 프로세스마다 handle이 다릅니다.

Code Flow 1: Creating a Dumb Buffer

가장 단순한 버퍼 생성 경로인 dumb buffer로 GEM을 따라가 보겠습니다. 화면에 소프트웨어로 그릴 때 쓰는 가장 기본적인 버퍼로, GPU 가속 기능은 없고 "CPU가 칠할 수 있는 평평한 메모리"입니다. 유저는 DRM_IOCTL_MODE_CREATE_DUMB 하나로 만듭니다.

순서를 보면 다음과 같습니다.

  2. drm_gem_handle_create()로 handle을 만듭니다. 안에서 drm_gem_object_handle_get()이 handle_count를 올리는데, 첫 번째 handle일 때만 객체 참조를 하나 잡습니다(if (obj->handle_count++ == 0) drm_gem_object_get(obj)). 이후 handle들은 개수만 올립니다.

Code Flow 2: Painting from the CPU with mmap

버퍼는 만들었지만 CPU에서 아직 접근할 수 없습니다. /dev/dri/card0 파일 하나에 여러 버퍼가 있으니, mmap(fd, ...)만으로는 어느 버퍼인지 알 수 없습니다. DRM은 이를 fake offset으로 풉니다. 파일의 오프셋(mmap의 마지막 인자)을 객체 식별자로 쓰는 것입니다.

Summary

이 Post 에서 확인한 것은 다음과 같습니다.
  • GPU 버퍼는 GEM 객체 하나로 표현되고, 유저는 fd(drm_file)마다 독립적인 handle로 가리킵니다. handle의 수명이 객체의 수명을 쥡니다.
  • dumb buffer는 shmem 파일 + mmap fake offset으로 구현되고, 페이지는 처음 필요할 때 확보됩니다.
  • mmap은 offset으로 객체를 찾아 page fault 때 페이지를 하나씩 연결합니다. 남의 버퍼를 offset만 알아서 매핑하지 못하게 drm_vma_node_is_allowed()가 막습니다.
handle은 이 drm_file 안에서만 의미가 있습니다. 다음에는 이 버퍼를 다른 프로세스나 다른 장치와 공유하는 방법, 즉 PRIME과 dma-buf를 봅니다.
